# API Contract: Zandy Touch

This is the contract between the frontend server (and the browser client) and the backend server. Both are built against it in parallel. Anything not listed here does not exist. The contract is the HTTP API only. The frontend server renders all HTML pages itself and gets its data through this API (section 12). The backend serves no HTML.

Builders request changes by message to the architect; they do not edit this file.

## 1. Conventions (apply to every endpoint)

### 1.1 Topology and origin

- Two separate servers: the frontend server (SSR pages, static assets) and the backend server (this API, photo media). Either may run as several instances. Neither keeps request state in process memory. Sessions, rate-limit counters, idempotency keys and stock all live in the backend's database, so any instance can answer any request.
- There is one public origin, `https://zandytouch.com` (decided in architecture.md). The edge routes by path: `/api/*` and `/media/*` go to the backend; every other path (pages, `/static/*`, `/healthz`, `robots.txt`, `sitemap.xml`) goes to the frontend server. The browser therefore calls the API same-origin with relative URLs such as `/api/products`: no CORS, no build-time API address, and the `zt_session` cookie works.
- The frontend server calls the backend at an internal base URL, `API_BASE_URL`, which it reads from its runtime configuration (never from a build setting), and it never reads Datomic. It forwards the incoming `X-Request-Id` (or generates one) to the backend. The backend reuses it in its logs and echoes it back.
- Client IP for rate limiting comes from the header named by the backend setting `CLIENT_IP_HEADER`. The edge sets that header from the verified client address and removes any value sent by the client. Public GET endpoints are not rate limited per IP, because the frontend server's own IP calls them; the edge protects them.

### 1.2 Format

- Base path `/api`. JSON in and out (`Content-Type: application/json`), except photo upload (multipart), the subscriber CSV export and media files.
- Every response carries `X-Request-Id`.
- Keys are camelCase. Dates and times are ISO 8601 in UTC with a `Z` suffix, e.g. `2026-10-24T09:30:00Z`. All timestamps are server-generated.
- Money: integer Ugandan shillings, no decimals, no floats. Objects that carry money also carry `currency: "UGX"`.
- IDs: opaque strings (UUIDs). Products also have a unique, human-readable `slug`. Orders have a human-readable `orderNumber` of the form `ZT-XXXXXX` (6 characters from an unambiguous uppercase alphabet) in addition to `id`.
- Phone numbers: accepted as `07xxxxxxxx` or `+2567xxxxxxxx` (spaces allowed). The server normalizes to E.164 (`+2567...`) and returns that.
- Unknown JSON keys are rejected with `validationFailed`. Strings are trimmed. Empty optional strings are treated as absent. No object uses data values (such as ids) as keys.
- Pagination: query `page` (from 1, default 1), `pageSize` (default 24, max 100). Response `{ "items": [...], "page": 1, "pageSize": 24, "totalItems": 87 }`.
- Route design: every path segment is either all-static or a single resource id. No static route is registered at the same position as a `{param}` route. This keeps the route table valid for either router the backend may use (Reitit, or Pedestal's own router as the documented fallback). Lookups use query strings or their own top-level resource.
- All validation is done on the server at the boundary (Malli) before business logic. Client validation is convenience only. Authorization is checked on the server on every protected endpoint.

### 1.3 Error shape (every error, every endpoint)

```
{ "error": { "code": "validationFailed", "message": "Please check the highlighted fields." } }
```

`code` is a stable camelCase string. `message` is a user-safe English sentence, never a stack trace.

Additive extension for forms and carts: `validationFailed`, `cartOutdated` and `agreementVersionOutdated` may include `error.details`, an array. Reason: forms and the cart need to attach messages to fields and lines. `code` and `message` are always present, so clients that ignore `details` still work.

```
{ "error": { "code": "validationFailed", "message": "Please check the highlighted fields.",
  "details": [ { "field": "customer.phone", "code": "invalidPhone", "message": "Enter a valid Uganda phone number." } ] } }
```

For `cartOutdated`, `details` entries are `{ "productId", "code": "priceChanged" | "soldOut" | "unavailable" | "insufficientStock", "message", "currentPrice"?, "availableQuantity"? }`. `availableQuantity` is present with `insufficientStock` (how many can still be ordered, at least 1; at 0 the code is `soldOut`).

### 1.4 Error codes and statuses

| HTTP | code | When |
|---|---|---|
| 400 | `malformedRequest` | Body is not valid JSON or has the wrong content type, or the `Idempotency-Key` header is present but not a UUID |
| 400 | `missingIdempotencyKey` | `Idempotency-Key` missing on a route that requires it |
| 401 | `unauthenticated` | No valid session on a staff endpoint |
| 401 | `invalidCredentials` | Wrong email or password |
| 403 | `forbidden` | Signed in but role not allowed (e.g. support calling an owner-only endpoint) |
| 403 | `csrfInvalid` | Missing or wrong `X-CSRF-Token` on a staff mutation |
| 403 | `passwordChangeRequired` | Session has `mustChangePassword: true` and the call is not the password change |
| 404 | `notFound` | Resource does not exist (or is draft or archived, on public endpoints) |
| 404 | `orderNotFound` | Order tracking mismatch (same message whether number or phone was wrong) |
| 409 | `cartOutdated` | Prices, availability or stock in the order differ from the server's. Nothing was stored and no stock was taken |
| 409 | `agreementVersionOutdated` | Submitted agreement version is not the current one |
| 409 | `idempotencyKeyReused` | Same key with a different payload |
| 409 | `versionConflict` | Optimistic concurrency: the record changed since the client loaded it (also a wrong `expectedQuantity` on a stock movement) |
| 409 | `invalidStatusTransition` | Order status change not allowed from the current status |
| 409 | `deliveryFeeRequired` | Confirming or approving delivery without a delivery fee set |
| 409 | `emailAlreadyInUse` | Staff email already exists |
| 409 | `cannotModifyOwner` | Attempt to deactivate or alter the owner account through the staff endpoints |
| 413 | `fileTooLarge` | Photo over 5 MB |
| 415 | `unsupportedMediaType` | Photo is not JPEG, PNG or WebP |
| 422 | `validationFailed` | Schema or business validation failed (with `details`) |
| 429 | `rateLimited` | Too many requests. Includes `Retry-After` |
| 500 | `internalError` | Unexpected. Logged with the request id |
| 503 | `serviceUnavailable` | `GET /api/healthz` only, when the database cannot be reached |

Codes that appear only inside `error.details` (with 422 `validationFailed`) or in a per-item result, never as the top-level code: `invalidPhone` and other field codes, `skuAlreadyInUse`, `priceRequired` and `imageRequired` (publishing a product without a price or an image), `stockCannotBeNegative`, `tooManyImages`, `priceChanged`, `soldOut`, `unavailable`, `insufficientStock`, `currentVersion`.

Per-file upload errors (inside a 201 response of `POST /api/admin/photos`) use `{ code, message }` with `fileTooLarge`, `unsupportedMediaType`, `dimensionsTooLarge` (over 6000 px on a side) and `unreadableImage`.

### 1.5 Caching

Public read endpoints are meant to be cached by the CDN, by the frontend server and by browsers. Rules:

- Public GET responses never set cookies and never send `Vary: Cookie`, otherwise shared caches refuse to store them. They carry an `ETag`, and the backend answers `If-None-Match` with 304.
- `stale-while-revalidate` lets a cache serve a slightly old copy while it refreshes in the background.
- Stock changes with every order, so any response that exposes availability has a short lifetime. A cached copy is only a display hint. The order endpoint is the single source of truth for stock and never relies on anything cached (section 4).
- Everything that carries personal data or is staff-only is `no-store`. So is every error response (4xx and 5xx), so that no cache keeps a failure.
- The frontend server fetches from the backend's internal URL, not through the CDN, so the pages it renders are as fresh as the page lifetime set in design-spec.md section 0.

| Endpoint | Cache-Control | Why this lifetime |
|---|---|---|
| `GET /api/site-info` | `public, max-age=300, stale-while-revalidate=600` | Configuration; changes rarely |
| `GET /api/delivery-areas` | `public, max-age=3600, stale-while-revalidate=3600` | Configuration |
| `GET /api/categories` | `public, max-age=60, stale-while-revalidate=300` | `productCount` changes when staff publish or sell out |
| `GET /api/policies/{type}` | `public, max-age=600, stale-while-revalidate=600` | Versioned text. A stale copy at checkout is caught by the version check (409 `agreementVersionOutdated`) |
| `GET /api/products` | `public, max-age=30, stale-while-revalidate=60` | Carries availability, which follows stock |
| `GET /api/products/{slug}` | `public, max-age=30, stale-while-revalidate=60` | Same. A client that wants a fresher value (the product page after load) sends request header `Cache-Control: no-cache`. Browser caches honour it and revalidate cheaply (304). A CDN does not honour a request-level `no-cache`, so through the CDN this value can be up to about 90 seconds old. The real stock check is always cart validation and order placement |
| `GET /api/sitemap-entries` | `public, max-age=3600` | Slugs only |
| `GET /media/{photoId}-{variant}.webp` | `public, max-age=31536000, immutable` | A photo id is never reused; a new upload is a new id |
| `GET /api/healthz` | `no-store` | |
| `POST /api/cart-validations` | `no-store` | POST; per-request |
| `POST /api/orders`, `POST /api/order-trackings` and everything else under `/api/auth`, `/api/admin` | `no-store` | Personal or staff data |

Effect to expect: after staff change a product or its stock, the storefront API answers can be up to about 90 seconds old (30 s plus the revalidation window). Staff screens (`/api/admin/**`) are always live.

### 1.6 Idempotency

- Header: `Idempotency-Key: <uuid generated by the client>`.
- Required (`missingIdempotencyKey` otherwise) on: `POST /api/orders`, `POST /api/admin/staff`, `POST /api/admin/staff/{id}/password-resets`, `POST /api/admin/products`, `POST /api/admin/products/{id}/stock-movements`, `POST /api/subscriptions`, `POST /api/contact-messages`, `POST /api/admin/photos`.
- A key is scoped to the method and path. The server stores the key with a hash of the request body and the identity of the result for 24 hours, in the database (so it works across instances).
  - Same key, same body: the original response is returned unchanged with `Idempotent-Replayed: true`, and no second side effect happens (no second order, no second stock decrement, no second email, no second acceptance record, no second stock movement).
  - Same key, different body: 409 `idempotencyKeyReused`.
  - Concurrent duplicates: only one takes effect; the other returns the first's result.
  - One-time secrets are never stored. A replay that would contain a `temporaryPassword` returns it as `null`.
- Natural-key idempotency: status changes (requesting the status the order already has returns 200 and changes nothing, including stock), `POST /api/subscriptions` (one record per email or phone), `PUT` and `PATCH` repeating the same change, `DELETE` of something already removed (204), `POST /api/admin/photo-assignments`.
- The client generates the order key when the checkout page loads and keeps it until the order succeeds or the cart contents change.

### 1.7 Authentication and authorization (staff)

- Session cookie `zt_session`: HttpOnly, Secure, SameSite=Lax, `Path=/api`, no `Domain` attribute, server-side session stored in the database, opaque random value. 12 hour sliding expiry, 7 day absolute lifetime. `Path=/api` means page requests carry no cookie, so rendered pages stay cacheable.
- CSRF: `GET /api/auth/sessions/current` returns `csrfToken`. Staff `POST`, `PUT`, `PATCH`, `DELETE` must send it as `X-CSRF-Token`. Public (guest) endpoints use no cookies, so they need no CSRF token.
- Roles: `owner`, `support`. Access labels: `public`, `staff` (owner or support), `owner`.
- Login is rate limited per IP and per email (5 failures in 15 minutes triggers a lockout). Passwords use a slow hash. Minimum length 10.
- Public mutating endpoints (`orders`, `subscriptions`, `contact-messages`, `order-trackings`) are rate limited per client IP (counters in the database) and accept an optional hidden honeypot field `website`, which must be empty or absent. A non-empty value gets a normal-looking success response and nothing is stored (no order, no stock taken).

## 2. Public: site info and reference data

### GET /api/site-info
Access: public. Cache: see 1.5.
Response 200:
```
{
  "businessName": "Zandy Touch",
  "tagline": "Beauty with Confidence",
  "phone": "+256706105779",
  "whatsapp": null,
  "email": null,
  "shopAddress": null,
  "openingHours": null,
  "currency": "UGX",
  "paymentMethods": ["cash", "mobileMoney"],
  "maxQuantityPerLine": 10
}
```
`whatsapp`, `email`, `shopAddress` and `openingHours` come from server configuration and are `null` until the owner confirms them (Q1, Q10, Q11). The frontend hides any null item. `email` here is the optional public contact address; it is not the sender and alert address, which is the owner email from configuration (`OWNER_EMAIL`) and is never exposed by default.

### GET /api/delivery-areas
Access: public. Cache: see 1.5.
```
{ "countries": [ { "code": "UG", "name": "Uganda", "cities": ["Kampala", "Entebbe", "Jinja", "Mbarara", "Gulu", "Mbale"] } ],
  "allowOtherCity": true }
```
Configuration; the city list is a placeholder until the owner supplies it (Q3). No fees are returned, because delivery cost is negotiated per order.

### GET /api/categories
Access: public. Cache: see 1.5.
```
{ "items": [ { "id": "…", "slug": "skincare", "name": "Skincare", "description": "…", "sortOrder": 1, "productCount": 14 } ] }
```
Seeded by migration with exactly six categories: `skincare`, `perfumes`, `body-shaping`, `body-care`, `weight-loss`, `health-and-wellness` (display name "Health & Wellness"). Dietary supplements and the weight-gain porridge belong to `health-and-wellness`. There is no Bedroom category. `productCount` counts published products (sold-out products included). Adding a category is a migration, not an admin feature in v1.

### GET /api/policies/{type}
Access: public. Cache: see 1.5. `type` is one of `orderTerms`, `termsOfSale`, `privacy`, `returns`; anything else is 404 `notFound`. (This replaces the earlier `/api/agreements/{type}`, which only served the order terms.)
```
{ "type": "orderTerms", "version": "2026-10-01", "title": "Order terms",
  "reviewStatus": "placeholder",
  "summary": ["Prices shown are product prices in UGX and exclude delivery.", "…"],
  "bodyBlocks": [
    { "type": "heading", "text": "1. Prices and delivery" },
    { "type": "paragraph", "text": "…" },
    { "type": "list", "items": ["…", "…"] } ],
  "contentHash": "sha256:…", "effectiveFrom": "2026-10-01T00:00:00Z" }
```
`reviewStatus` is `placeholder` (drafted text awaiting human review) or `approved`. While `placeholder`, the frontend shows a visible notice "Draft text, not yet reviewed". `summary` may be an empty array for documents that do not need one. `bodyBlocks` types are `heading`, `paragraph`, `list` only; all text is plain text and must be escaped by the frontend. Exactly one version of each type is current; older versions are kept. `contentHash` is the SHA-256 of the source text and is what the acceptance record stores. Only `orderTerms` is accepted at checkout. The `orderTerms` text itself must cover: prices exclude delivery, the fee is agreed before dispatch, cancellation before dispatch, payment on delivery, being reachable, returns, and how personal data is used. Policy documents are delivered by backend migration; there is no editor in v1.

### GET /api/sitemap-entries
Access: public. Cache: see 1.5. Used by the frontend server to build `sitemap.xml`.
```
{ "products": [ { "slug": "glow-serum", "updatedAt": "…" } ],
  "categories": [ { "slug": "skincare" } ],
  "generatedAt": "…" }
```
Published products only (sold out included).

## 3. Public: catalogue

A product is *published* when its status is published. Stock rules for the public view:
- `stockQuantity` is an integer ≥ 0 held by the backend. It is never returned to the public.
- `availability` is `available` when stock > 0 and `soldOut` when stock is 0.
- `maxQuantity` is the most a customer may order of this product now: `min(maxQuantityPerLine, stock)`, and 0 when sold out.

### GET /api/products
Access: public. Cache: see 1.5. Published products only (sold out ones included, flagged).
Query (all optional): `categorySlug`, `q` (2 to 80 characters; case-insensitive substring match against name, brand, short description and description), `availability` (`available` or `soldOut`), `ownBrand` (`true`), `featured` (`true`), `sort` (`newest` default, `priceAsc`, `priceDesc`, `nameAsc`), `page`, `pageSize`.
```
{ "items": [ {
    "id": "…", "slug": "glow-serum", "name": "Glow Serum", "brand": "Zandy Touch", "isOwnBrand": true,
    "categorySlug": "skincare", "price": 85000, "currency": "UGX",
    "shortDescription": "…", "availability": "available", "maxQuantity": 10, "isNew": true, "featured": false,
    "image": { "id": "…", "alt": "…", "urls": { "thumb": "/media/ab12-thumb.webp", "medium": "/media/ab12-medium.webp", "large": "/media/ab12-large.webp" } }
  } ],
  "page": 1, "pageSize": 24, "totalItems": 87 }
```
`price` is always present for published products (the server refuses to publish without one). `image` is the first image, or `null`. `isNew` is true for 30 days after first publish. Sold-out products sort after available ones within any sort, so the grid leads with what can be bought.
Errors: 422 for an unknown `sort` or bad paging. An unknown `categorySlug` returns an empty list.

### GET /api/products/{slug}
Access: public. Cache: see 1.5. Published products only.
```
{ "id": "…", "slug": "glow-serum", "name": "Glow Serum", "brand": "Zandy Touch", "isOwnBrand": true,
  "category": { "slug": "skincare", "name": "Skincare" },
  "price": 85000, "currency": "UGX", "availability": "available", "maxQuantity": 10, "isNew": true,
  "shortDescription": "…", "description": "…plain text, blank line separates paragraphs…",
  "size": "30 ml", "howToUse": "…", "ingredients": "…",
  "images": [ { "id": "…", "alt": "…", "urls": { "thumb": "…", "medium": "…", "large": "…" } } ],
  "related": [ /* up to 4 summary items, same shape as the list items */ ],
  "updatedAt": "2026-10-20T08:00:00Z" }
```
`size`, `howToUse`, `ingredients` are `null` when empty. Text is plain text and must be escaped by the frontend. `updatedAt` reflects catalogue edits, not stock changes.
Errors: 404 `notFound` for an unknown slug, a draft or an archived product.

### POST /api/cart-validations
Access: public. Refreshes the browser cart against the server's prices and stock. Writes nothing and reserves nothing. Cache: `no-store`.
```
{ "items": [ { "productId": "…", "quantity": 2 } ] }
```
Rules: 1 to 20 lines, quantity 1 to `maxQuantityPerLine`, no duplicate `productId`.
Response 200:
```
{ "items": [ { "productId": "…", "slug": "…", "name": "…", "unitPrice": 85000, "quantity": 2, "lineTotal": 170000,
               "availability": "available", "maxQuantity": 10, "purchasable": true,
               "image": { "…": "…" } or null, "problem": null } ],
  "itemsSubtotal": 170000, "currency": "UGX",
  "deliveryFee": null, "deliveryFeeNote": "Agreed with you before dispatch",
  "hasProblems": false }
```
`problem` is `null`, `"soldOut"` (stock 0), `"insufficientStock"` (stock is above 0 but below the requested quantity; `maxQuantity` says how many can be ordered) or `"unavailable"` (removed or draft). `purchasable` is false for problem lines, and they do not count toward `itemsSubtotal`. The response never contains a computed delivery fee. A "problem-free" result here is not a promise: stock can still run out before the order is placed.

## 4. Public: orders

### POST /api/orders
Access: public (guest). Requires `Idempotency-Key`. Rate limited. Cache: `no-store`.
```
{
  "customer": { "name": "Amina Nakato", "phone": "0771234567", "email": "amina@example.com", "preferredContact": "whatsapp" },
  "delivery": { "countryCode": "UG", "city": "Kampala", "area": "Ntinda", "addressLine": "Plot 12, Minister's Village Rd", "directions": "Blue gate next to the pharmacy" },
  "paymentMethod": "mobileMoney",
  "note": "Please call after 5pm",
  "items": [ { "productId": "…", "quantity": 2, "expectedUnitPrice": 85000 } ],
  "agreement": { "type": "orderTerms", "version": "2026-10-01" },
  "website": ""
}
```
Field rules:
- `customer.name` 2 to 100. `customer.phone` required, valid Uganda number. `customer.email` optional, valid email. `customer.preferredContact` `phone` or `whatsapp`.
- `delivery.countryCode` `UG` for now. `city` is one of the listed cities, or free text 2 to 60 when `allowOtherCity` is true. `area` 2 to 80. `addressLine` 3 to 200. `directions` optional, up to 300.
- `paymentMethod` `cash` or `mobileMoney` (a preference; nothing is charged online).
- `note` optional, up to 500. `items` 1 to 20 lines, quantity 1 to `maxQuantityPerLine`, unique `productId`s. `expectedUnitPrice` is the price the customer saw.
- `agreement` is required and its `version` must equal the current `orderTerms` version. This is the explicit acceptance; nothing is implied or defaulted.
- There is no field for a delivery fee. The server never accepts or computes one at this point.

Server behaviour:
1. Validate the schema (422 `validationFailed`).
2. Check `agreement.version` (409 `agreementVersionOutdated`, with `details: [{ "field": "agreement.version", "code": "currentVersion", "message": "2026-11-01" }]`).
3. In one atomic Datomic transaction (a transaction function, so the check and the write cannot be separated, and two instances or two simultaneous requests cannot both take the last unit):
   a. Load each product. Each must be published, its current price must equal `expectedUnitPrice`, and its `stockQuantity` must be at least the ordered quantity.
   b. If any line fails, nothing is written and the response is 409 `cartOutdated` with a `details` entry per failing line (`priceChanged`, `soldOut`, `unavailable` or `insufficientStock` with `availableQuantity`). All failing lines are reported in one response.
   c. Otherwise: reduce each product's stock by the ordered quantity; create the order with a price snapshot per line (`status: "placed"`, `deliveryFee: null`, `version: 1`); write one stock movement of type `order` per line (linked to the order); create the agreement acceptance record linked to the order (customer name and phone, `acceptedAt` server time, `type`, `version`, `contentHash`); create the history entry `placed`; queue the notification emails.
4. Emails are sent after commit by a background worker (section 9a). Email failure never fails the order and is logged.

A rejected request (409, 422) leaves stock and data untouched. A replay of a successful request (same key) returns the original order and does not take stock again, even if stock has since run out.

Response 201 (a replay returns 200 with the same body and `Idempotent-Replayed: true`):
```
{
  "order": {
    "id": "…", "orderNumber": "ZT-7K3P9Q", "status": "placed", "placedAt": "2026-10-24T09:30:00Z",
    "customer": { "name": "Amina Nakato", "phone": "+256771234567", "email": "amina@example.com", "preferredContact": "whatsapp" },
    "delivery": { "countryCode": "UG", "city": "Kampala", "area": "Ntinda", "addressLine": "…", "directions": "…" },
    "paymentMethod": "mobileMoney", "note": "…",
    "items": [ { "productId": "…", "name": "Glow Serum", "unitPrice": 85000, "quantity": 2, "lineTotal": 170000 } ],
    "itemsSubtotal": 170000, "currency": "UGX",
    "deliveryFee": null, "deliveryFeeNote": "Agreed with you before dispatch", "total": null
  },
  "agreementAcceptance": { "type": "orderTerms", "version": "2026-10-01", "acceptedAt": "2026-10-24T09:30:00Z" }
}
```
`total` is `null` until staff record the delivery fee.

### POST /api/order-trackings
Access: public. Rate limited (10 per minute per IP). POST so the phone number never appears in a URL or log. Creates nothing. Cache: `no-store`.
Request: `{ "orderNumber": "ZT-7K3P9Q", "phone": "0771234567" }`
Response 200:
```
{ "orderNumber": "ZT-7K3P9Q", "status": "confirmed", "placedAt": "…",
  "items": [ { "name": "Glow Serum", "unitPrice": 85000, "quantity": 2, "lineTotal": 170000 } ],
  "itemsSubtotal": 170000, "deliveryFee": 10000, "total": 180000, "currency": "UGX",
  "paymentMethod": "mobileMoney", "city": "Kampala",
  "timeline": [ { "status": "placed", "at": "…" }, { "status": "confirmed", "at": "…" } ] }
```
No street address, email, staff names or internal notes. `status` is `placed`, `confirmed`, `approvedForDelivery`, `delivered` or `cancelled`; the frontend shows friendly labels (Received, Confirmed, On its way, Delivered, Cancelled). `deliveryFee` and `total` are `null` until set. Errors: 404 `orderNotFound` (one message for both mismatches), 422.

## 5. Public: newsletter and contact

### POST /api/subscriptions
Access: public. Requires `Idempotency-Key`. Rate limited.
Request: `{ "email": "amina@example.com", "phone": null, "consent": true, "source": "footer", "website": "" }`
At least one of `email` or `phone`. `consent` must be `true`. `source` is `footer`, `orderConfirmation` or `home`. The server stamps the record with a `consentTextVersion`.
Response 201 (200 if already subscribed, same body): `{ "subscribed": true }`. Never reveals whether the address already existed.

### POST /api/unsubscribes
Access: public. Request `{ "token": "…" }` (from the unsubscribe link). Response 200 `{ "unsubscribed": true }`. Unknown tokens also return 200. Missing token: 422.

### POST /api/contact-messages
Access: public. Requires `Idempotency-Key`. Rate limited.
Request: `{ "name": "…", "phone": "…", "email": null, "message": "…", "website": "" }`. `name` 2 to 100, at least one of `phone` or `email`, `message` 10 to 1000.
Effect: stored and emailed to the owner (a mail failure is logged, not shown). Response 201 `{ "received": true }`.

## 6. Staff authentication and account

### POST /api/auth/sessions
Access: public. Request `{ "email": "…", "password": "…" }`.
Response 201 and `Set-Cookie: zt_session`:
```
{ "user": { "id": "…", "name": "Sandra", "email": "…", "role": "owner", "mustChangePassword": false }, "csrfToken": "…" }
```
Errors: 401 `invalidCredentials` (same message for unknown email, wrong password and deactivated account), 429.

### GET /api/auth/sessions/current
Access: staff. Same body as login, status 200, fresh CSRF token. 401 `unauthenticated` without a session.

### DELETE /api/auth/sessions/current
Access: staff. Signs out. 204, also when already signed out.

### POST /api/auth/password-resets
Access: public. Request `{ "email": "…" }`. Always 202 `{ "requested": true }`. A reset email goes to the owner address only if the email belongs to the owner account. Rate limited.

### PUT /api/auth/password-resets/{token}
Access: public. Request `{ "newPassword": "…" }` (at least 10 characters, not in a small common-password list). Response 200 `{ "passwordChanged": true }`. Token is single use, valid 60 minutes; all the user's sessions end. Errors: 404 `notFound`, 422.

### PUT /api/admin/account/password
Access: staff. Allowed while `mustChangePassword` is true. Request `{ "currentPassword": "…", "newPassword": "…" }`. Response 200 `{ "passwordChanged": true }`. Clears `mustChangePassword`; other sessions end. Errors: 401 `invalidCredentials`, 422.

## 7. Staff: orders

There is no endpoint to create an order as staff. Orders come only from `POST /api/orders`.

Status values: `placed`, `confirmed`, `approvedForDelivery`, `delivered`, `cancelled`.
Allowed transitions: placed to confirmed; confirmed to approvedForDelivery; approvedForDelivery to delivered; placed, confirmed or approvedForDelivery to cancelled. Others return 409 `invalidStatusTransition`. `delivered` and `cancelled` are final.

"Dispatch" means the move to `approvedForDelivery`. Stock rule on cancel: cancelling from `placed` or `confirmed` (before dispatch) restores the stock of every line, atomically with the status change, as a stock movement of type `orderCancelled`. Cancelling from `approvedForDelivery` (for example the customer refuses on arrival) does not restore stock automatically, because the goods have left; staff adjust stock by hand when the goods return (section 8.3). Stock is restored at most once per order.

### GET /api/admin/orders
Access: staff. Cache: `no-store`.
Query: `status`, `q` (order number, customer name or phone), `page`, `pageSize` (default 25), `sort` (`placedAtDesc` default, `placedAtAsc`).
```
{ "items": [ { "id": "…", "orderNumber": "ZT-7K3P9Q", "status": "placed", "placedAt": "…", "customerName": "Amina Nakato",
               "customerPhone": "+256771234567", "city": "Kampala", "itemCount": 2, "itemsSubtotal": 170000,
               "deliveryFee": null, "total": null, "currency": "UGX", "paymentMethod": "mobileMoney", "updatedAt": "…" } ],
  "page": 1, "pageSize": 25, "totalItems": 41,
  "counts": { "placed": 3, "confirmed": 2, "approvedForDelivery": 1, "delivered": 30, "cancelled": 5 } }
```

### GET /api/admin/orders/{id}
Access: staff. Response 200:
```
{ "order": { "…same fields as order in POST /api/orders…", "version": 3, "staffNote": null,
             "deliveryFee": 10000, "total": 180000, "paymentMethodUsed": null, "cancelReason": null,
             "stockRestored": false },
  "agreementAcceptance": { "type": "orderTerms", "version": "2026-10-01", "contentHash": "sha256:…",
                           "acceptedAt": "…", "customerName": "Amina Nakato", "customerPhone": "+256771234567" },
  "history": [ { "status": "placed", "at": "…", "by": null, "note": null },
               { "status": "confirmed", "at": "…", "by": { "id": "…", "name": "Grace" }, "note": "Fee agreed by phone" } ] }
```
404 `notFound` if unknown.

### PATCH /api/admin/orders/{id}
Access: staff. Records the agreed delivery fee and an internal note on an open order (`placed`, `confirmed` or `approvedForDelivery`). Order lines cannot be edited.
Request (at least one field besides `version`): `{ "version": 3, "deliveryFee": 10000, "staffNote": "Customer prefers evening" }`
`deliveryFee`: integer UGX 0 to 1,000,000 (0 means free). `staffNote` up to 1000. Setting `deliveryFee` records who set it and when. Response 200 `{ "order": { … } }` with `version` incremented. Errors: 409 `versionConflict`, 409 `invalidStatusTransition` (order is final), 422.

### POST /api/admin/orders/{id}/status-changes
Access: staff. How orders are processed, including **approve delivery**.
Request: `{ "version": 3, "status": "approvedForDelivery", "note": "Boda rider booked", "paymentMethodUsed": null, "cancelReason": null }`
Rules:
- `confirmed` and `approvedForDelivery` require a delivery fee already recorded (409 `deliveryFeeRequired`). Dispatch is therefore impossible without the agreed fee on the order.
- `delivered` requires `paymentMethodUsed` of `cash` or `mobileMoney`.
- `cancelled` requires `cancelReason` (3 to 300 characters) and restores stock as described above.
- `note` optional, up to 300.
- If the order already has the requested status: 200, current order, no new history entry, no stock change.
Response 201 for a new change (200 for a no-op): `{ "order": { … }, "stockRestored": false }`. `stockRestored` is true when this change returned stock. Errors: 409 `versionConflict`, `invalidStatusTransition`, `deliveryFeeRequired`, 422.
Side effects: history entry with staff id and time; the customer's tracking view changes immediately. No customer email on status changes in v1 (the receipt is sent at placement only).

## 8. Staff: products, stock and photos

### 8.1 Products

Product write fields:
`name` (2 to 120), `brand` (1 to 80), `isOwnBrand` (boolean), `categorySlug` (must exist), `price` (integer UGX, 100 to 100,000,000, or `null` while the product is a draft), `shortDescription` (up to 200), `description` (up to 4000, plain text), `size` (optional, up to 40), `howToUse` (optional, up to 1000), `ingredients` (optional, up to 1000), `featured` (boolean), `status` (`draft` or `published`), `sku` (optional, up to 40, unique, used for photo matching), `images` (ordered array of up to 6 entries `{ "id": "<existing photo id>", "alt": "<up to 140 characters, optional>" }`; first is the main image).

Publishing rule (server enforced, 422 with `details`): a product can only be `published` if it has a `price` (`priceRequired`), at least one image (`imageRequired`) and a category. A published product cannot have its price set to `null`. Stock is not required to publish; a product published with zero stock shows as sold out.

Stock is not a product write field after creation. `stockQuantity` is accepted only on create (as the opening stock). From then on it changes only through orders and stock movements (8.3), so a staff member saving the product form can never overwrite stock changed by an order in the meantime. For the same reason, stock changes do not increment the product `version`; only edits to the fields above do.

The `slug` is generated from the name on creation, made unique, and does not change when the name is edited.

### GET /api/admin/products
Access: staff. Cache: `no-store`. Query: `status` (`draft`, `published`, `archived`; default excludes archived), `categorySlug`, `q` (name, brand or SKU), `stock` (`out` for 0, `low` for 1 to the low-stock threshold, which is 5), `page`, `pageSize` (default 25), `sort` (`updatedAtDesc` default, `nameAsc`, `stockAsc`).
Items: `id`, `slug`, `sku`, `name`, `brand`, `isOwnBrand`, `categorySlug`, `price` (null for an unpriced draft), `currency`, `stockQuantity`, `availability`, `lowStock` (boolean), `status`, `featured`, `image` (first image or `null`), `updatedAt`, `updatedBy: { id, name }`. Response also includes `counts: { "out": 2, "low": 3 }` for the filter tabs (published products).

### GET /api/admin/products/{id}
Access: staff. All write fields plus `id`, `slug`, `version`, `stockQuantity`, `availability`, `lowStock`, `images` (full objects `{ id, alt, urls }`), `createdAt`, `updatedAt`, `updatedBy`. Includes archived products.

### POST /api/admin/products
Access: staff. Requires `Idempotency-Key`. Request: write fields plus optional `stockQuantity` (integer 0 to 100000, default 0). Required: `name`, `brand`, `categorySlug`, `status`. `price` is required when `status` is `published`, and may be omitted or `null` for a draft. Others default to empty, `isOwnBrand` false, `featured` false. If `stockQuantity` is above 0, a stock movement of type `initial` is written in the same transaction. Response 201: the product (shape of GET by id). Errors: 422 (a duplicate SKU is `skuAlreadyInUse` in `details`; publishing without a price is `priceRequired`).

### PATCH /api/admin/products/{id}
Access: staff. Partial update. Request `{ "version": 5, …any write fields except stockQuantity… }`; sending `stockQuantity` is rejected as an unknown key. When `images` is present it replaces the list. Response 200: the product with `version` incremented. Errors: 404, 409 `versionConflict`, 422 (`skuAlreadyInUse`, `priceRequired`, `imageRequired`). A price change only affects future orders (existing orders keep their snapshot). Setting `status: "published"` on an archived product restores it (the same publishing rule applies).

### DELETE /api/admin/products/{id}
Access: staff. Archives the product: it leaves the storefront, search, sitemap and category counts; orders and stock history are untouched. 204; repeating returns 204.

### 8.2 Photos

### POST /api/admin/photos
Access: staff. Bulk upload to the photo library. `multipart/form-data`, field `files`, 1 to 20 files per request, JPEG, PNG or WebP, up to 5 MB each, at most 6000 px per side. Requires `Idempotency-Key`.
Response 201:
```
{ "items": [ { "filename": "GT-SERUM-01.jpg", "status": "stored",
               "photo": { "id": "…", "urls": { "thumb": "…", "medium": "…", "large": "…" }, "assignedProductIds": [] },
               "suggestedProductId": "…", "error": null },
             { "filename": "huge.png", "status": "rejected", "photo": null, "suggestedProductId": null,
               "error": { "code": "fileTooLarge", "message": "This file is larger than 5 MB." } } ] }
```
One bad file does not fail the others. The server creates thumb (480 px wide), medium (800) and large (1200) WebP variants (never enlarging), applies EXIF orientation and strips EXIF location data. File type is detected from the content. `suggestedProductId` is set when the file name starts with an existing product `sku` (case-insensitive). Malformed request: 400; more than 20 files: 422.

### GET /api/admin/photos
Access: staff. Query `unassigned` (`true`), `page`, `pageSize` (default 40). Items `{ id, filename, urls, assignedProductIds, uploadedAt }`.

### POST /api/admin/photo-assignments
Access: staff. Request `{ "assignments": [ { "photoId": "…", "productId": "…" } ] }` (1 to 100 entries). Each photo is appended to the product's images (max 6; extras reported per entry).
Response 200: `{ "results": [ { "photoId": "…", "productId": "…", "status": "assigned" }, { "photoId": "…", "productId": "…", "status": "rejected", "error": { "code": "tooManyImages", "message": "…" } } ] }`. Repeating an assignment returns `assigned` with no change.

### DELETE /api/admin/photos/{id}
Access: staff. Deletes the photo and detaches it from products (a published product left with no photos becomes a draft). 204; repeat 204.

### 8.3 Stock

### POST /api/admin/products/{id}/stock-movements
Access: staff. Adjusts stock by a signed amount. Requires `Idempotency-Key`. Cache: `no-store`.
Request: `{ "delta": 20, "reason": "restock", "note": "Supplier delivery 24 Oct", "expectedQuantity": 3 }`
- `delta`: non-zero integer, absolute value up to 100000. Positive adds, negative removes.
- `reason`: `restock`, `stocktake`, `shopSale` (sold over the counter in the physical shop), `damagedOrLost`, `returnedGoods`, `other`.
- `note`: optional, up to 300.
- `expectedQuantity`: optional. When present, the adjustment is applied only if the current stock equals it, else 409 `versionConflict`. The "Set to counted number" screen uses this: it sends `delta = counted - shown` together with `expectedQuantity = shown`, so an order arriving in the meantime does not get overwritten.
The change is atomic, like order placement. It cannot take stock below 0 (422, detail code `stockCannotBeNegative`).
Response 201:
```
{ "movement": { "id": "…", "type": "adjustment", "reason": "restock", "delta": 20, "quantityAfter": 23,
                "note": "…", "orderNumber": null, "at": "…", "by": { "id": "…", "name": "Grace" } },
  "stockQuantity": 23, "availability": "available" }
```
Errors: 404, 409 `versionConflict`, 422.

### GET /api/admin/products/{id}/stock-movements
Access: staff. Paginated (default 25), newest first. Items have the movement shape above. `type` is `initial`, `adjustment`, `order` (system, one per order line, with `orderNumber`) or `orderCancelled` (system, with `orderNumber`). `by` is `null` for system entries from customer orders.

## 9. Staff: messages and subscribers

### GET /api/admin/contact-messages
Access: staff. Query `page`, `pageSize` (default 25). Items `{ id, name, phone, email, message, receivedAt }`, newest first. Read-only in v1.

### GET /api/admin/subscribers
Access: staff. Query `page`, `pageSize` (default 50), `format` (omit for JSON, or `csv`). JSON items `{ id, email, phone, subscribedAt, source, active, unsubscribeUrl }`. `unsubscribeUrl` is an absolute link built from the configured site base URL (`SITE_BASE_URL`), e.g. `https://zandytouch.com/unsubscribe?token=…` in production. With `format=csv` the response is `text/csv` with the same columns for active subscribers only; any cell starting with `=`, `+`, `-` or `@` is prefixed with a single quote. The owner sends campaigns manually from this export.

### 9a. Emails (side effects, not endpoints)

All site emails are sent from the owner email address given in configuration (`OWNER_EMAIL`, from business-context.md). SMTP credentials are environment variables. Mail is queued in the database in the same transaction as the event that causes it, and sent after commit by a background worker, which retries a few times. With several backend instances, exactly one instance sends each message. A failure is logged with the order or message id and never fails the request. The site-wide daily cap `MAIL_DAILY_CAP` (default 400) stops sending below the mail provider's own daily limit; messages beyond it stay queued and go out when the window allows. The owner password-reset email is also sent from the owner address, directly rather than queued.

| Trigger | To | Content |
|---|---|---|
| New order placed | the owner, plus every staff member with `notifyOnNewOrder` | Order number, customer name and phone, city, items and subtotal, link `/admin/orders/{id}` |
| New order placed, only if `customer.email` was given | the customer | Receipt: order number, items, subtotal, "delivery fee to be agreed", how to reach the shop |
| Contact message | the owner | The message and contact details |
| Owner password reset | the owner | Reset link, valid 60 minutes |

## 12. How the frontend server uses this API

The frontend server owns all HTML routes (the page list is in design-spec.md section 1), SEO tags, `robots.txt`, `sitemap.xml`, its own `/healthz`, and the static bundle, CSS, fonts and icons, all served under `/static/` (for example `/static/design-tokens.css`, `/static/assets/fonts/...`, `/static/js/main.<hash>.js`). For SSR pages it calls the API server-side at its internal `API_BASE_URL` (not through the CDN), renders the same Replicant views the browser uses, embeds the data in `<script id="initial-state" type="application/json">` (with `<` escaped) and the browser reuses it without refetching.

| Page | API calls made by the server (in parallel where independent) |
|---|---|
| `/` | `GET /api/categories`, `GET /api/products?sort=newest&pageSize=8`, `?ownBrand=true&pageSize=4`, `?featured=true&pageSize=8`, `GET /api/site-info` |
| `/shop` | `GET /api/products` with the query string, `GET /api/categories` |
| `/categories/{slug}` | `GET /api/categories`, `GET /api/products?categorySlug=…`. Unknown slug: HTTP 404 page |
| `/products/{slug}` | `GET /api/products/{slug}`. 404 from the API gives an HTTP 404 page |
| `/about`, `/contact` | `GET /api/site-info` |
| `/delivery-and-payment` | `GET /api/delivery-areas` |
| `/legal/terms-of-sale`, `/legal/privacy`, `/legal/returns-and-refunds`, `/legal/order-terms` | `GET /api/policies/{type}` for `termsOfSale`, `privacy`, `returns`, `orderTerms` |
| `/sitemap.xml` | `GET /api/sitemap-entries` |
| `/cart`, `/checkout`, `/order-placed`, `/track-order`, `/unsubscribe`, `/admin/**` | None on the server. These are a document shell (`noindex`); the browser calls the API |

Every SSR page also gets `GET /api/site-info`. Failure handling: if the API is unreachable or returns 5xx, the frontend returns HTTP 503 with a calm error page and `Retry-After`, with `Cache-Control: no-store`, and must not let a CDN cache that response. If the API is slow, use a short timeout (about 3 seconds) rather than hanging the page. SSR page cache lifetimes are in design-spec.md section 0 and must not exceed the API's lifetimes by much, so stock staleness stays bounded. Catalogue pages may also carry `stale-if-error` so the CDN can keep serving them while the backend restarts (architecture.md, decision D2).

Launch gate: when the frontend server runs with `SITE_INDEXABLE=true` it checks the four policy documents at start-up and refuses to start while any has `reviewStatus: "placeholder"`.

The browser calls the API directly for cart validation, order placement, tracking, forms and all admin actions.
