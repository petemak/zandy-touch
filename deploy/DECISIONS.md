Fixed by architecture and standards (not owner choices): three JVM processes plus edge proxy on one server, Datomic Pro with dev storage, nightly backups with a tested restore, same-origin routing, SITE_INDEXABLE=false on staging.
Edge proxy (my choice, no cost): Caddy (automatic HTTPS, path routing, health checks, X-Upstream and X-Client-Ip headers). Containers: Docker Compose on the VPS.

Deployment design (deployment-engineer, 26 October 2026): Docker Compose on the VPS (reason in deploy/compose.yaml header), Caddy 2.11 as the edge proxy, Datomic Pro 1.0.7745 transactor in its own container with dev storage on a host directory, images built on the deploying machine (the one with the SSH key) and loaded over SSH, static files copied additively to the host, backups by systemd timers using rclone to R2. Deploys run from the machine that holds the SSH key (pjm); the account holder adds that public key to the VPS.

Staging-only variant (26 October 2026): `deploy/compose.small.yaml` is merged over `deploy/compose.yaml` on a 4 GB host (`COMPOSE_FILE` in the server's compose `.env`; `HOST_ROLES=staging`). Only the transactor, Caddy and the staging backend and ssr run; no production env file is needed; Caddy loads only `caddy/sites/staging.caddy`. Adjustment to D3, recorded as D3 allows: the transactor runs with -Xmx512m (D3: 1024m), memory-index 16m/128m and object cache 64m, container limit 1152m. Evidence: a real Datomic Pro 1.0.7745 transactor took the full application schema plus 144,000 entities (about 90 MB) without errors; RSS 430 MB idle, 983 MB after the load. Heaps total 1216 MB, container limits 2756 MB, expected loaded total about 2.1 GB plus OS 0.5 GB on a 3.8 GB host. Must be re-measured on the real host (RUNBOOK, "What to measure on staging").
Backups on the staging-only host: production does not exist there and staging holds sample data, so the nightly timers are NOT enabled and `backup.sh` without options does nothing. `backup.sh --staging` and `restore-test.sh --staging` exercise the whole mechanism (backup-db, archive, R2 upload under `staging-trial/`, restore, counts) once, to satisfy check D-3 early. The timers are enabled on the server that runs production.

Staging server set up (26 October 2026, deployment-engineer): OVH VPS-1 141.95.0.8, Ubuntu **26.04 LTS** (not 24.04), user `ubuntu`, key login only (password login disabled after a second key session was confirmed; `PermitRootLogin no`). `server-setup.sh` ran: Docker 29.9.2 from Docker's own `resolute` repository, Compose 5.6.1 (needs 2.24+), rclone 1.75.2, babashka 1.13.226, ufw (22, 80, 443 only), 2 GB swap, unattended security updates, `/srv/zandy` and `/etc/zandy`. One fix was needed for 26.04: it ships uutils coreutils, whose `install -o 10001` refuses a user id that has no account, so the script now creates directories and then `chown`s by number.
Staging mail (owner, 26 Oct 2026, Gmail app password not available yet): staging sends to a **local mail sink** (`mailsink` service in compose.small.yaml, `deploy/mailsink/sink.py`, python:3.13-alpine, 64 MB limit, no published port). `staging.env` has SMTP_HOST=mailsink, SMTP_PORT=2525, SMTP_USER=sink and SMTP_PASSWORD=mail-sink-accepts-any-password (a dummy the sink accepts; not a secret, not a Gmail password). Every message is decoded into the sink's log; read it with `/srv/zandy/bin/show-mail.sh`. Switch to Gmail: RUNBOOK "Switching staging mail to Gmail".
Staging release naming: `deploy.sh staging` accepts a dirty tree only with `ALLOW_DIRTY=yes` and names the release `<commit>-wip<hash of the uncommitted state>`. Production never accepts this. Commit the deployment files before go-live so production can be built from a plain commit id.
ACME contact address is optional now (no personal address is sent to Let's Encrypt unless the owner sets ACME_EMAIL in /srv/zandy/compose/.env).

Problems found and fixed on the way (all in deploy/ or scripts/ops/, no application source):
- Datomic 1.0.7745 health endpoint dies on a 2 vCore host ("Insufficient configured threads: required=3 < max=3"): transactor command in compose.small.yaml gets -XX:ActiveProcessorCount=8 (4 and 1 still failed, 8 worked).
- ssr's Java HttpClient opens with an h2c upgrade; Caddy forwarded it and the backend answered 400, so every page was "unavailable": the internal listeners now drop Upgrade and HTTP2-Settings.
- `find -exec touch {}` form rejected on the host: deploy.sh uses a loop. Local build needs docker-buildx. The Datomic zip download once hung for 12 minutes inside the build; a retry worked.
- Two-instance smoke test used curl's cookie jar, which neither stores nor sends the Secure session cookie over plain http: scripts take the cookie from Set-Cookie.
Memory on the real host (2 vCore, 3814 MB, no swap used, nothing OOM-killed, no restarts): see the staging report; measured by scripts/ops/burst-test.sh (twin backend with the staging limits and a throw-away database; 4 x 20 pictures of 4.8 MB; 100 orders in 30 s): peaks transactor 735 MiB, backend 514 MiB, ssr 172 MiB, caddy 21, sink 16; peak sum 1425 MiB; lowest host available 1668 MiB. Idle after the bursts: transactor about 800 MiB (it keeps what it mapped; limit 1152). Production on a VPS-1 would add roughly 250 MB to the backend (D3 heaps) so the decision rule (peak total under 2.6 GB, more than 1.2 GB free) looks met, with the transactor as the item to watch. Not decided here.

Staging through Cloudflare (26 October 2026, proxy on, record Proxied): D-5 FAILED 8/10 because no "eligible for cache" rule is in effect (/shop and /api/products stay cf-cache-status DYNAMIC); bypass checks pass. The Free-plan minimum edge TTL is NOT yet measured, because nothing is cached. Cloudflare also adds max-age=14400 to /robots.txt (Browser Cache TTL not "Respect existing headers") and drops the ETag on no-cache pages. Real visitor addresses reach Caddy correctly (client_ip = visitor via CF-Connecting-IP; a spoofed header on a direct connection is ignored). D-3 still blocked: backup.env R2 key values unchanged (not valid keys).

Staging through Cloudflare, re-run after the owner added the two cache rules and the step-3 settings (26 October 2026): D-5 PASSED 10/10. /shop and /api/products are HIT on the second fetch (largest Age 54 s and 21 s, under the 100 s limit), so Cloudflare Free honours the short s-maxage values and the minimum-edge-TTL risk does not apply. /admin, /admin/login, /api/admin/orders, /api/auth/sessions/current and any request with zt_session are DYNAMIC, never HIT. D-1 11/11 and the cache-header check 48/48 through the proxy (missing ETag accepted on uncached no-cache pages behind the CDN); HTTPS: 301 to https, TLS 1.3, HSTS once from the origin; Caddy logs the real visitor IP from CF-Connecting-IP. Email Address Obfuscation was switched off by the owner (Security, Settings, "Client side abuse"). This supersedes the 8/10 entry above.

D-3 done on staging (26 October 2026): backup and restore pass. Two script fixes were needed: the Datomic CLI hard-codes -Xms1g, so the tools are now called with -Xms64m -Xmx384m; and Datomic refuses to restore a backup into a storage that already holds that database (":restore/collision" even under another name), so restore-test.sh restores into a throw-away second transactor (zandy-restore-tx, tmpfs storage). check-cache-headers.sh accepts a missing ETag on uncached no-cache pages when the response carries cf-ray; direct-to-origin it stays strict (48/48 both ways). A firewall restriction to Cloudflare ranges is recommended in RUNBOOK.md, not applied.
